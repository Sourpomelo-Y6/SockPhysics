# Sock Physics 段階的実装プラン

作成日: 2026-09-08

仕様の基準: [SockPhysics_DesignSpec.md](SockPhysics_DesignSpec.md)

## 方針と現在地

Unity 2021.3.45f2 / URP 2Dの初期構成から開始する。計画作成時点でゲーム固有のC#スクリプトは未実装。

最優先は「ほぼ閉じた靴下へ足を押し込むと柔らかく開き、抜くと閉じる」挙動の成立。その後に「押す → 引っかかる → 戻す → 角度を変える → 再び押す」という攻略を追加する。現実の布の完全再現より、操作感・安定性・状態の分かりやすさを優先する。

以下の保持方法、入力方式、判定方式は実装時に検証する仮案であり、仕様書の確定事項を置き換えるものではない。

## 実装の順序

各段階を小さな実装・動作確認・コミットの単位とする。完了条件を確認してから次へ進む。

| 段階 | 実装範囲 | 完了条件 |
| --- | --- | --- |
| 1. 足の操作 | 専用検証シーン、仮の足のRigidbody2DとCollider2D、マウスドラッグ、壁、リセット | 足を前後上下に動かせる。壁に押し当てても簡単に突き抜けず、初期状態に戻せる |
| 2. 靴下の骨組み | 上下2列の物理ポイント、隣接Joint、線による仮表示 | 足が触れると布が変形し、放置しても暴れない |
| 3. 閉じる・開く挙動 | 狭い初期間隔、上下の復元力、靴下を保持する仕組み | 足を入れると開き、抜くと閉じる。繰り返しても破綻しない |
| 4. Prototype 1の調整 | 摩擦・柔らかさ・復元力などのInspector設定、貫通対策 | 押し込む感触があり、設定による挙動の違いを確認できる |
| 5. 足首と引っかかり | LegとFootの分割、足首Joint、角度操作、狭い足首区間 | 押し続けると進みにくく、戻して角度を変えると通れる |
| 6. 直線ステージの完成 | 簡単なかかとの膨らみ、閉じたつま先、位置評価、クリア表示 | 正しく履くとクリアでき、再挑戦できる |
| 7. 90度ステージの形状 | 曲がった靴下、曲がりに沿った部位配置と進行度評価 | 角度を調整して曲がり部分を通過できる |
| 8. 押し戻しの攻略ルール | BendResistance、押し当てと引き戻しの判定、抵抗の表示、柔らかさなどへの反映 | 押す・戻す・再び押すことで抵抗が減り、攻略につながる |

仕様書との対応: 段階1〜4がPrototype 1、段階5がPrototype 2、段階6がPrototype 3、段階7〜8がPrototype 4。

## 物理実装で検証する点

### 布の当たり判定

Joint自体はポイント間の当たり判定を作らない。足がポイントの隙間から抜けないよう、段階2〜4でポイント間隔とColliderサイズを検証する。必要なら区間にも当たり判定を追加する。

### 靴下の保持

全ポイントを自由に動かすと靴下全体が押し流される可能性がある。初期案では入口付近を緩く保持し、保持の強さを調整可能にする。入口を押し広げる動作を妨げないことを確認する。

### 足のマウス追従

Transformの直接変更による瞬間移動を避け、マウス位置へ力で追従する方式を第一候補にする。追従力と速度に上限を設け、速いドラッグでも物理挙動が安定するか確認する。

### 引き戻す操作の意味

BendResistanceを接触中に毎フレーム減らす方式にはしない。「押し当て成立 → 一定距離戻す → 次の押し当て」の単位で抵抗を減らす案とする。接触の細かな振動を複数回の押し当てとして数えないようにする。段階7では形状の通過を検証し、段階8でこの攻略ルールを加える。

### クリア判定

段階6で足先・かかと・足首などの位置評価を導入する。各許容範囲、Fitの重み、過度な伸びの扱いはプレイ検証で決める。単に足先が奥の判定領域へ触れただけでクリアしないことを確認する。

## コード構成を増やす順序

- 初期は靴下生成・物理制御、足の操作、仮表示に必要な構成だけを用意する。SockController、SockPhysicsPoint、FootControllerを基本候補とする。
- 部位差を導入するときにSockSection、足を分割するときにFootPartを追加する。
- クリア判定時にFitEvaluator、90度攻略時にBendControllerを追加する。
- 調整項目はまずInspectorで公開する。Prototype 1で必要な項目が見えてからSockDataのScriptableObject化を行う。
- ステージ追加や将来機能のためだけの大規模な抽象化は先行させない。

## 検証方針

各段階でUnityのコンパイルとPlay Modeでの動作を確認する。物理段階では速いドラッグ、長押し、繰り返しの抜き差し、放置、リセットを試し、貫通・振動・過度な伸び・初期状態の復元を確認する。

Fit計算や抵抗値更新など数値で判定できるルールを追加した段階では、自動テストも追加する。押しっぱなしでは抵抗が減り続けないこと、引き戻し後に再度減少できること、不正な位置ではクリアしないことを対象にする。

## Git管理とフォントの復元

既存の未コミットのローカルGitリポジトリを初回コミットの基盤とする。Assets、Packages、ProjectSettings、DocsとGit設定を管理し、Library、Logsなどの生成物は既存の.gitignoreに従って除外する。

フォントはローカルに残し、Git管理から除外する。対象はFontsフォルダ、TextMesh ProのFonts & Materialsフォルダ、元フォントファイル、SDFフォントアセット、および対応する.meta。フォント専用フォルダ内のアトラス・マテリアルも対象となる。新規の生成フォントもこれらのフォルダに配置する。

別環境ではフォントを別途復元する必要がある。TextMesh Proの標準・サンプルフォントは対応するEssential Resources / Examples & Extrasの再インポートで復元する。Assets/FontsのNoto Sans JPと生成SDFは別途用意する。既存参照を維持する場合は元の.metaも含めて復元し、再生成した場合はTMP設定やシーンの参照を再割り当てする。フォントを除外したクローンだけでは既存TMPサンプルの文字表示は保証されない。

既存の.gitattributesは画像等にGit LFSを指定しているため、別環境でもGit LFSを用意する。今回の作業はローカルコミットまでとし、リモートリポジトリの作成・公開は含まない。
